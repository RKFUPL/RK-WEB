## Exact specifications

### rk_authentication_otp

Category: **AUTHENTICATION**. Language: **en_US**. Backend event(s): `signup_otp`, `login_otp`, `forgot_password_otp`.

Handler: `auth.signup_request_otp / request_otp / forgot_password_request_otp (explicit WhatsApp request)`.

Parameter order and types:

1. `code` ? otp; exact six-digit code generated by the existing authentication service.

Exact message content:

```text
*{{1}}* is your verification code. For your security, do not share this code.
```

Meta controls authentication wording; use the Authentication editor, select **Copy code**, enable the security recommendation, and set expiry to **10 minutes**. The footer is `This code expires in 10 minutes.` This matches the existing server OTP validity; it does not extend a code's absolute expiry after queueing. Do not enter a custom utility body. The copy code button label is `Copy code`.

Submission component specification (for manual review/submission; this app does not call a create-template endpoint):

```json
{
  "name": "rk_authentication_otp",
  "language": "en_US",
  "category": "AUTHENTICATION",
  "components": [
    {
      "type": "BODY",
      "add_security_recommendation": true
    },
    {
      "type": "FOOTER",
      "code_expiration_minutes": 10
    },
    {
      "type": "BUTTONS",
      "buttons": [
        {
          "type": "OTP",
          "otp_type": "COPY_CODE",
          "text": "Copy code"
        }
      ]
    }
  ]
}
```

Sending supplies the same code in a text BODY parameter and the index `0` URL subtype BUTTON parameter, as prescribed for authentication OTP delivery. No code is written to delivery logs, consent audit records, or application logs. The outbox encrypts it and removes its payload after processing. Worker and HTTP retries reject expired, consumed, superseded, or exhausted challenges. A new explicit OTP request uses a new challenge/hash; transport retries reuse the original idempotency key.

Signup and password recovery have separate optional WhatsApp OTP checkboxes. The existing `/api/auth/request-otp` login verification API accepts `whatsappOtpConsent: true`; password login itself does not request an OTP or send WhatsApp. Password reset and account recovery use the existing forgot-password challenge. Optional transactional signup consent is separate from the one-time OTP request, and neither enables marketing. Email remains independent.

## Business proof and remaining integrations

- Order confirmation requires a saved confirmed fulfillment state and paid order. A paid order awaiting availability confirmation does not emit the confirmation template; its later recorded confirmation uses the same idempotency key.
- Payment confirmation follows successful verified capture only, with the recorded payment reference and actual amount/currency. It may be separate from availability confirmation.
- Shipping requires persisted dispatch time, courier and tracking ID. Filling previously missing details can queue the dispatch notification. A courier/AWB identity queues once; URL/note/date-only edits do not resend. A replacement courier or AWB creates a separate shipment event, and old queued shipment identities are skipped. Legacy tracking-update callers use this same shared shipped event, avoiding a second message.
- Out-for-delivery and delivery follow saved fulfillment transitions. RK-WEB currently records courier states through authorized staff/admin workflows, not a live courier API. Staff must record observed courier status, not predict it. A future courier connector needs its own verified source integration; none is invented here.
- Cancellation follows a successful stored cancellation transition.
- Refund processed follows a signature-verified Razorpay `refund.processed` event with matching payment, currency, positive amount and actual refund ID. It supports partial refunds and deduplicates per refund ID. Manually choosing a refunded order status, or recording external refund initiation, does not prove that a refund was processed and cannot emit this catalogue message. No refund is initiated by this feature.
- Authentication requests are rate limited; codes expire in ten minutes, permit five attempts and are consumed atomically once. Queued work rechecks the live challenge, current consent/number, opt-outs and template status before using the existing transport. Only explicit Meta rate-limit rejections retry; ambiguous timeouts/5xx remain held/unknown and require reconciliation. Neither queue nor Meta can promise exactly-once delivery; permanent event/message claims prevent blind application resends.

## Consent and opt-out

Signup and checkout show the optional transactional consent wording from `whatsapp_catalogue.CONSENT_TEXT`; the frontend uses the matching shared wording. Marketing preferences remain separate. The private `whatsapp_consents` audit stores customer ID, phone, category, enabled/status, timestamp, source and optional order ID. Order-specific checkout consent stays tied to that order and number. Merely checking an existing legacy boolean without consent metadata is insufficient; obtain new consent through signup/checkout/profile.

Signed inbound STOP/STOPALL/UNSUBSCRIBE/CANCEL/END/QUIT messages create a durable keyed phone block and withdraw matching account consent. Raw inbound text is discarded. The queue and both local test modes respect the block. Retries can finish a partially recorded opt-out; already processed STOP duplicates cannot revoke later explicit consent. Re-enable only through fresh explicit customer consent in preferences or checkout, not an admin test checkbox. A one-time authentication request does not override STOP.
